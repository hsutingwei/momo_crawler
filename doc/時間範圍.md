# 時間範圍（Time Range）

本文件用於明確定義本研究的時間相關設定：**觀測期間（observation window）**、**標籤切分日/截點日（label split / cutoff date）**，以及**建模時可用資訊的截止日（避免資料洩漏）**。

---

## 1️⃣ 欄位與時間語意

在資料表查詢中（以 `product_comments pc` 為主）：

- **評論時間（event time）**：`pc.comment_date`  
  - 代表評論「發生」的日期/時間（使用者在平台留下評論的時間）。
  - 研究中凡是「評論行為在時間上的變化」與「時間窗統計特徵」原則上都應以此欄位為準。

- **爬取時間（ingestion / capture time）**：`pc.capture_time`  
  - 代表爬蟲「取得/寫入」該評論到資料庫的日期/時間。
  - 用於判定「在某個時間點 \(T\) 做預測時，哪些資料**已經可得**」，以避免把 \(T\) 之後才爬到的資料誤用到 \(T\) 當下的特徵（資料洩漏）。

> 核心區分：  
> **`comment_date` 是事件發生時間；`capture_time` 是資料進庫時間。**  
> 當需要「as-of \(T\)」的可用資料集時，通常要同時限制 `comment_date <= T` 與 `capture_time <= T`。

---

## 2️⃣ 觀測期間（Observation Period）

### 2.1 定義

- **觀測期間**：本研究納入分析的評論事件範圍  
  \[
  [D_{start},\; D_{end}]
  \]
  其中 \(D_{start}\) 與 \(D_{end}\) 以 **`pc.comment_date`** 的最小/最大值（或研究設計指定的邊界）定義。

### 2.2 實務建議（可重現寫法）

- **資料收集上限（as-of 上限）**：若要描述你「實際爬到」的資料邊界，請以 `pc.capture_time` 的範圍補充一組區間：
  \[
  [C_{start},\; C_{end}]
  \]

### 2.3 SQL：查出 comment / capture 的起訖

（依你提供的 join 結構，以下以整體資料集為例）

```sql
-- 觀測期間（以評論時間 comment_date）
select
  min(pc.comment_date) as comment_date_start,
  max(pc.comment_date) as comment_date_end
from product_comments pc;

-- 爬取期間（以 capture_time）
select
  min(pc.capture_time) as capture_time_start,
  max(pc.capture_time) as capture_time_end
from product_comments pc;
```

如需依 keyword / 商品檢查：

```sql
select
  p.keyword,
  min(pc.comment_date) as comment_date_start,
  max(pc.comment_date) as comment_date_end,
  min(pc.capture_time) as capture_time_start,
  max(pc.capture_time) as capture_time_end,
  count(*) as comment_rows
from product_comments pc
left join products p on pc.product_id = p.id
group by p.keyword
order by p.keyword;
```

## 3️⃣ 標籤切分日（Label Split Date / Cutoff）

### 3.1 定義

- **標籤切分日（或特徵截點日）**：\(T\)  
  - 在 \(T\) 當下建立特徵（feature），並以 \(T\) 之後的資訊建立標籤（label）或目標變數。
  - 你若已在其他文件定義過（例如 `論文研究說明文件.md` 的 Time Definition：`T = 2025-06-25`），本文件沿用該 \(T\)。

> 註：若你的實驗設計不是單一 \(T\)，而是多個 rolling cutoffs（多個 \(T_1, T_2, ...\)），請在本節補上 cutoffs 產生規則（例如每 7 天取一次）。

### 3.2 SQL：快速檢查 \(T\) 前後資料量

```sql
-- 請把 :T 替換為你的 cutoff（例如 '2025-06-25'）
select
  count(*) filter (where pc.comment_date <= :T) as n_comment_le_T,
  count(*) filter (where pc.comment_date >  :T) as n_comment_gt_T
from product_comments pc;
```

## 4️⃣ 預測資訊只用到哪一天（Information Availability / Anti-Leakage）

本研究若以「在時間點 \(T\) 做預測」為前提，則所有可用於產生特徵的資訊必須滿足：

- **事件發生不晚於 \(T\)**：`pc.comment_date <= T`
- **資料在 \(T\) 前已被爬到/入庫**：`pc.capture_time <= T`

### 4.1 as-of \(T\) 的評論資料集（建議）

```sql
-- as-of T 的可用評論（避免使用 T 之後才爬到的資料）
select p.keyword, pc.*
from product_comments pc
left join products p on pc.product_id = p.id
where pc.comment_date <= :T
  and pc.capture_time <= :T
order by p.keyword, pc.comment_date;
```

### 4.2 常見情境說明

- **情境 A：只看事件時間（較寬鬆）**  
  - 僅限制 `comment_date <= T`。  
  - 風險：若某些評論雖然發生在 \(T\) 前，但其實是在 \(T\) 之後才被爬到（`capture_time > T`），那在「\(T\) 當下」其實不可得，會造成資訊穿越。

- **情境 B：as-of 可得性（較嚴謹，建議用於論文敘述）**  
  - 同時限制 `comment_date <= T` 與 `capture_time <= T`。  
  - 好處：可明確宣稱「模型在 \(T\) 當下能看到的資料」。

## 5️⃣ 需要你填入/固定的三個日期（最終寫法）

把本節當成論文可直接引用的三行定義，將日期補齊即可：

- **觀測期間（以 `pc.comment_date`）**：\(D_{start}=\) `____-__-__`，\(D_{end}=\) `____-__-__`
- **標籤切分日（cutoff）**：\(T=\) `____-__-__`
- **預測資訊截止**：僅使用滿足 `comment_date <= T` 且 `capture_time <= T` 的資料
